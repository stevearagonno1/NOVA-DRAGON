# Module 10: قاعدة التليمتري الرئيسية — The Quant Matrix

## 5.1 المبدأ
> **يجب أن يعمل البوت كمختبر تنقيب بيانات (data-mining laboratory).**
> **كل صفقة مُنفَّذة** (في وضعي الاختبار الرجعي **والحي**) **يجب أن تُسجَّل في قاعدة بيانات SQLite محلية** باسم **`master_log.db`** باستخدام **مخطط (schema) شديد التحسين والنحافة**.

## 5.2 مخطط قاعدة البيانات — Schema Definition

| العمود | النوع | المحتوى |
|--------|-------|---------|
| **`Market_Regime`** | TEXT | الحالة الكلية الدقيقة لحظة الدخول (مثال: `"Trending Bull"`، `"Volatile Shock"`) |
| **`Symbol_and_Setup`** | TEXT | الرمز ونوع الإعداد (مثال: `"BTCUSDT \| Monotonic_MSS_FVG"`) |
| **`Telemetry_JSON`** | TEXT | كائن JSON مُسلسَل يلتقط **القيمة الرقمية الدقيقة والتوقّع (BUY/SELL/HOLD) لكل مؤشر** تم تقييمه عند الدخول (مثال: ميل KAMA، احتمالية Naive-Bayes، دلتا CVD، RSI) |
| **`Exit_Trigger`** | TEXT | الآلية الدقيقة التي أغلقت الصفقة (مثال: `"Dynamic ATR Trailing"`، `"Micro Time-Stop"`، `"Hard Stop"`) |
| **`Net_Outcome`** | REAL | **صافي نسبة الربح/الخسارة النهائية بعد محاكاة احتكاك المنصة البالغ 0.2%** ذهاباً وعودة |

> 🎯 **الغرض من `Market_Regime` + `Telemetry_JSON`:** أن تتمكن لاحقاً من الإجابة على السؤال المحوري: **«متى تنجح الاستراتيجية ومتى تفشل؟»** عبر فلترة بسيطة.

## 5.3 منطق تصدير البيانات — Data Export Logic
- نفّذ **دالة غير متزامنة (async)** تستعلم قاعدة SQLite، تُنسّقها، وتُصدّرها **كملف CSV**.
- **يجب** أن يفرز استعلام SQL المخرجات لتجميع الحالات المتشابهة معاً وترتيبها حسب الأداء:
```sql
ORDER BY Market_Regime ASC, Net_Outcome DESC
```

# Module 11: واجهة تلغرام غير المتزامنة والإشعارات المُدارة بالأحداث

## 5.4 القاعدة المعمارية
> **وحدة تلغرام يجب أن تكون غير متزامنة بالكامل. يجب ألا تحجب أو تبطئ حلقة بيانات السوق الرئيسية (WebSocket) أبداً.**

### مهمة الاستطلاع — Polling Task
- نفّذ حلقة **long-polling مستمرة على `/getUpdates`** باستخدام **`aiohttp`**.
- شغّلها **كمهمة في الخلفية** عبر **`asyncio.create_task()`**.

### وضع التخفّي — Stealth Mode
- **يجب أن يعمل البوت بصمت.**
- 🚫 **لا تُرسل رسائل تلقائية لكل دخول أو خروج صفقة.**

### الإنجازات المُدارة بالأحداث — Event-Driven Milestones
أرسل إشعارات تلقائية **فقط** عند هذه الأحداث النظامية المحددة:

| # | الحدث | نص الرسالة |
|---|-------|-----------|
| 1 | **Boot & Connect** | `⚡ تم تشغيل وربط المحرك بنجاح (النظام في وضع الاستعداد - لم يبدأ تنفيذ الصفقات)` |
| 2 | **Start Executing** | `🚀 تم تأكيد الأمر: بدأت عملية تنفيذ الصفقات في الخلفية` |
| 3 | **Progress Thresholds** | احسب الحجم المكتمل مقابل الهدف، وأصدِر تنبيهات عند **10% و 25% و 50% و 75% و 90%** بالضبط |
| 4 | **Completion** | `🏁 اكتمل تنفيذ الصفقات بنسبة 100% بنجاح` |

### لوحة الأزرار المضمّنة — Inline Keyboard Dashboard
**ألصق هذه اللوحة بالضبط** بكل رسائل الإنجازات والردود اليدوية:

```
[ 📊 تقرير الحالة ] [ 🚀 بدء التنفيذ ]
[ ⏸ توقف مؤقت    ] [ 🛑 توقف تام وتصفير ]
[ 📥 تصدير السجل الشامل ]
```

### معالجة النداءات الراجعة — Callback Handling
عندما يُضغط أي زر مضمّن، **يجب على البوت الإقرار به فوراً** باستخدام نقطة النهاية **`answerCallbackQuery`** — لإيقاف **عجلة التحميل (loading spinner)** على شاشة المستخدم.

# Module 12: قالب الحالة الصارم ومعالجات تصدير الملفات

## 5.5 زر الحالة — `btn_status`
يجب أن يرد **بهذا القالب النصي بالضبط**، مملوءاً ديناميكياً، **بدون أي قوائم عملات نشطة أو حشو**:

```
🟢 الناجحة: {win_percentage}%
🔴 الخاسرة: {loss_percentage}%
اجمالي المكاسب: {net_pnl_dollars}$
نسبة النجاح: {win_rate}%
إجمالي الصفقات التقريبية لكل اسبوع: {weekly_avg}
```

## 5.6 زر التصدير — `btn_export_log`
- يُشغّل دالة **تصدير SQLite إلى CSV**.
- يُرسل ملف `.csv` أو `.txt` الناتج **مباشرةً إلى دردشة تلغرام كرفع مستند (`sendDocument`)**.
- ⚙️ **يجب تغليف عملية الإدخال/الإخراج هذه في `asyncio.to_thread()`** لمنع **تجميد حلقة الأحداث (event loop)**.

## 5.7 أزرار التحكم

| الزر | الوظيفة |
|------|---------|
| **`btn_start_trade`** | يبدّل راية التنفيذ العامة إلى `True` |
| **`btn_pause`** | يبدّلها إلى `False` (يوقف الدخولات الجديدة، ويدير المراكز المفتوحة) |
| **`btn_stop_reset`** | يبدّل الراية إلى `False`، **يصفّر كل مقاييس الجلسة في الذاكرة**، و**يعيد تعيين جدول الجلسة في SQLite** |

# تعليمات التسليم النهائي (Final Delivery Instructions)

## 5.8 مواصفات الكود النهائي
- اجمع **كل الوحدات (5 دفعات / 12 وحدة)** في **سكربت بايثون واحد جاهز للإنتاج وشديد التحسين**.
- استخدم **أفضل ممارسات `asyncio` لإدارة الحالة**: **`asyncio.Lock()`** للقواميس المشتركة.
- تأكد أن **كل حسابات المؤشرات مُتّجهة (vectorized) بالكامل** عبر **numpy / pandas** — لمنع **اختناق المعالج (CPU throttling)** في بيئات الهاتف المحدودة.
- أخرج الكود النهائي **كملفات `.py` قابلة للتنزيل**.

# إدارة ملفات المشروع (قرار هندسي مهم)

## 5.9 لماذا نحذف النسخ القديمة فوراً؟

### أسباب حذف النسخ القديمة:
1. **منع التشتت البرمجي / تلويث السياق (Context Pollution):**
   وجود نسخ متعددة مثل **`NOVA.BOT.ZERO.WAIT`** و **`NOVA V7.0`** (و`NOVA.BOT.ZERO.WAIT.py.txt`، و`NOVA.BOT.ZERO.RISK.py.txt`) في نفس مساحة العمل **يربك الوكيل المبرمج**، مما قد يدفعه لـ:
   - دمج **أكواد متناقضة**، أو
   - **العودة لتقنيات قديمة ألغيناها**.
2. **توفير مساحة السياق (Context Window):**
   مسح مئات الأسطر البرمجية القديمة **يحرّر الذاكرة اللحظية للوكيل**، مما يجعله **يسخّر كامل طاقته التحليلية لفهم البوت الجديد وتطوير الفلاتر الكمية المعقدة بدقة**.
3. **تجنّب تداخل المسارات والأخطاء:**
   بقاء ملفات الأكواد القديمة قد يسبب **استدعاءات خاطئة (ImportErrors)** أو **قراءة ملفات ذاكرة قديمة تُعطّل عمل النظام**.

## 5.10 الملفات التي يجب أن تبقى في مصادر المشروع

| الملف | لماذا يبقى |
|-------|-----------|
| **ملف البوت الجديد الموحّد** (الذي جهّزه الوكيل) | هو الأساس |
| **الملفات التشغيلية المرافقة** | مثل `start.sh` وملفات البيئة `env` والأجزاء المقسّمة مثل `engine.py` إذا كان البوت مقسّماً |
| **المخطط الهندسي الشامل (Master Blueprint)** | المرجع النظري |
| **ملف خلاصة المؤشرات (Knowledge Base)** | الذي نستخرج منه التطويرات القادمة |
| **كافّة الملفات المعنونة بالعربية** (التحليلات، المخططات، المستندات الكمية) | لأنها **المرجع النظري والاستراتيجي لتطويرنا القادم** |

## 5.11 نصيحة السلامة
> احتفظ بـ **نسخة احتياطية من البوتات القديمة في مجلد خارجي على هاتفك** للرجوع إليها للضرورة،
> **ولكن امسحها تماماً من صندوق المصادر** (سواء في Gemini أو عند الوكيل) لتبدأ بصفحة بيضاء نقية.

# مراجعة كود الوكيل المبرمج (بعد أول بناء)

## 5.12 نقاط القوة التي تحققت بنجاح

| النقطة | التفصيل |
|--------|---------|
| **الهندسة اللامتزامنة (Async Purity)** | تخلّص تماماً من أوامر `requests` البطيئة واستخدم **`aiohttp`** و **`websockets`** |
| **محرك البيانات المزدوج** | بنى فئة **`NovaEngine`** القادرة على قراءة البيانات التاريخية **Parquet** للاختبار، **أو** استلام البيانات الحية من بينانس عبر **LiveFeed** — **دون أي تغيير في منطق التحليل** |
| **تصنيف السوق كمراقب فقط** | تم بناء وحدة **`regime.py`** لتصنيف السوق (صاعد، هابط، متذبذب، متفجّر) **دون حظر الصفقات** — وهو ما يطابق قاعدة **«القبول الصفري» (Zero-Threshold)** لتسجيل كل الفرص |
| **التنفيذ اللحظي وإدارة المخاطر** | نفّذ أمر **`LIMIT_MAKER`** عند أفضل سعر عرض/طلب (**bookTicker**)، وطبّق قاعدة مهلة الـ **12 ثانية (Hanging Bullet)** لإلغاء الأمر المعلق إذا هرب السعر |
| **تلغرام الصامت والتفاعلي** | تم بناء **`telegram_bot.py`** ليعمل في الخلفية **دون تعطيل أسعار السوق**، مع أزرار **تصدير السجل الشامل (csv)** والتقارير المرحلية |
| **مسارات العملات** | ضبط مسار البيانات التاريخية ليكون داخل ترمكس **`~/crypto_archive`** مع مراعاة **الأسماء القديمة للعملات** (مثل `RNDR` و `GRAM`) لضمان عدم توقف الاختبار |

## 📌 ملخص الدفعة الخامسة

1. **كل صفقة** (رجعية أو حية) تُسجَّل في **`master_log.db`**.
2. الأعمدة: `Market_Regime` · `Symbol_and_Setup` · `Telemetry_JSON` · `Exit_Trigger` · `Net_Outcome`.
3. التصدير بـ `ORDER BY Market_Regime ASC, Net_Outcome DESC`.
4. تلغرام **async كامل** عبر `aiohttp` و `asyncio.create_task()`، **وضع تخفٍّ**، إشعارات عند 5 أحداث فقط.
5. لوحة أزرار مضمّنة من 5 أزرار + `answerCallbackQuery` لإيقاف عجلة التحميل.
6. التصدير عبر `sendDocument` داخل `asyncio.to_thread()`.
7. التجميع النهائي: سكربت واحد، `asyncio.Lock()` للحالة المشتركة، حسابات **متّجهة بالكامل**.
8. **نظّف المصادر من النسخ القديمة**، واحتفظ بنسخة خارجية، وأبقِ الملفات العربية والمخطط الهندسي.
